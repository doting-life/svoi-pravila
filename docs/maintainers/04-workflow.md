## 2. Жизненный цикл задачи

1. **Промпт.** Claude выдаёт промпт **в чате** (на английском), с номером `NNNN` и веткой в заголовке: цель, контекст, требования, вне скоупа, приёмочные критерии, формат отчёта. Промпты в репозитории не хранятся.
2. **Передача.** Владелец вставляет промпт в чат Cursor.
3. **Реализация.** Cursor работает в ветке `task/NNNN-slug`, коммиты по Conventional Commits.
4. **Блокер.** Если требование противоречиво, невыполнимо без обходного пути или требует решения вне скоупа — Cursor **останавливается** и пишет отчёт со статусом `BLOCKED` и конкретным вопросом. Импровизация запрещена.
5. **Отчёт.** Финальный ответ Cursor в чате по шаблону ниже; владелец передаёт его Claude. В репозиторий отчёты не коммитятся.
6. **Проверка.** Claude получает отчёт и ветку. Claude читает **diff и исходный код**, запускает гейты сам, сверяет с промптом. Отчёт — только навигация, не доказательство.
7. **Вердикт.** `ACCEPT` → владелец мержит. `CHANGES REQUIRED` → промпт `NNNN-a` в чате с перечнем дефектов; исправление в той же ветке.
8. **Живые вызовы LLM — только с бюджетом.** Промпт, требующий обращений к провайдеру, содержит раздел «Live budget» (модели, операции, подмножество кейсов, повторы, максимум токенов). Без него исполнитель провайдера не вызывает (`.cursor/rules/60-live-provider-budget.mdc`).
9. **Технический долг не копится.** Любой дефект, найденный при проверке, исправляется до мержа, даже если он «мелкий».

## 3. Гейты
Единая точка запуска — `make check`. Состав (расширяется промптами):
- `ruff check`, `ruff format --check`
- `mypy --strict`
- `lint-imports` (границы слоёв)
- `pytest` с порогом покрытия (общий ≥ 95 %, `domain` и `application` — 100 % строк и веток)
- `pip-audit`
- `gitleaks`
- `alembic` — проверка, что модели и миграции синхронны, и что миграции обратимы
- после 0014: `biome check`, `tsc --noEmit`, `vitest --coverage`, сборка

CI вызывает цели `make` и дополнительно проверяет, что ветки `task/*` не изменяют CTO-owned пути (`AGENTS.md`, `.cursor/`, `docs/maintainers/`).

### Локальный паритет с CI (решение владельца 05.10)
- CI — зеркало, а не способ найти ошибки. `make ci` локально запускает всё, что запускает GitHub: гейты бэкенда и мини-приложения, поиск секретов, сборку и скан образов, smoke-тест стека, проверку CTO-owned путей. Задания workflow вызывают только цели `make`; логики в YAML нет.
- Версии инструментов закреплены в репозитории; `make ci` сначала сверяет локальные версии с закреплёнными.
- Git-хуки (`make hooks`): при коммите — быстрые проверки формата и линтеров по изменённым файлам; при push — `make ci`.
- **Два уровня проверок (решение владельца 07.10: меньше времени и токенов):**
  - во время работы — только `make quick`: формат, линтер, типы и тесты затронутых модулей, секунды;
  - полный `make ci` — один раз, автоматически, хуком перед push на отправляемом коммите. Вручную перед push его не запускают, повторных прогонов «для отчёта» нет.
- **`make ci` выводит только сводку по этапам.** Полные логи пишутся в `.ci-logs/` (в `.gitignore`); при ошибке на экран попадают последние 40 строк упавшего этапа.
- Push — один раз за раунд проверки, только после зелёного `make ci` на том же коммите. Коммиты-исправления «чтобы позеленел CI» запрещены.
- Красный CI после зелёного локального `make ci` — дефект паритета: исполнитель останавливается, сообщает, какое задание и чем отличается, и чинит паритет.
- Задание CI = одно общее составное действие установки инструментов + `make ci JOB=<имя>`. Версии читаются только из нативных файлов пинов (их понимают и сами инструменты, и действия установки). Первый шаг каждого задания — `toolchain-check`. Список заданий задан один раз, его совпадение с workflow проверяется автоматически.
- `make ci` герметичен:
  - не читает и не пишет `.env` владельца — окружение создаётся во временном файле вне репозитория;
  - работает в отдельном compose-проекте на своих портах и удаляет его вместе с томами;
  - на чистом клоне ставит зависимости сам;
  - pre-push проверяет именно отправляемый коммит во временном worktree.
- CTO при проверке запускает те же гейты; части, требующие Docker, подтверждаются отчётом `make ci` и зелёным CI.

### Экономия токенов исполнителя (решение владельца 10.10)
Исполнитель тратит токены на всё, что читает и ждёт. Поэтому:
- **Проверки по области изменений.** Хук перед push и проверки PR запускают только задания, которые изменение может затронуть. Правило одно для хука и GitHub:
  - только документация — быстрые задания (секреты, CTO-пути);
  - бэкенд или мини-приложение — их гейты, сборка образов и smoke стека;
  - развёртывание, Dockerfile, CI, скрипты, пины, неизвестный путь — всё.

  Push в `master` и ночной запуск на GitHub всегда полные: ни одна сборка не публикуется без полной проверки.
- **Скан образов не блокирует задачи** (ADR-0012). Новая уязвимость в чужом образе — отдельная задача CTO, а не работа внутри текущей.
- **Исполнитель не ждёт GitHub CI.** Отчёт пишется сразу после push. За GitHub следят владелец и CTO.
- **Скриншоты снимает CTO** при проверке (скрипт `miniapp/scripts/screenshots.mjs`). Исполнитель снимает их, только если промпт называет конкретные экраны.
- **Короткий отчёт.** Шаблон — в `.cursor/rules/00-executor-contract.mdc`; CTO проверяет код сам, перечни файлов и таблицы покрытия не нужны.
- **Промпт — это план.** Режим планирования Cursor для промптов CTO не включается: план уже написан.
- **Документы CTO не гоняют тяжёлые проверки.** Коммит, меняющий только документы, в хуке проходит за секунды. Push документов CTO по возможности объединяется с ближайшим слиянием задачи.
- **В `master` попадают только два вида изменений:** документы CTO и squash-слияние принятой задачи. Любой другой код — только через задачу и вердикт.

## 6. Ветки и коммиты
- Основная ветка — `master` (решение владельца 03.10). Она защищена: только через PR, зелёный CI, вердикт `ACCEPT`, слияние squash-ом.
- CTO-документы (`AGENTS.md`, `.cursor/`, `docs/maintainers/`) Claude коммитит сам напрямую в `master` коммитами `docs(cto): …`, не трогая рабочее дерево и ветки задач (решение владельца 03.10). Push — владелец или Cursor по его поручению.
- Squash-merge принятой ветки в `master` и push может выполнять Cursor по прямому поручению владельца — только после вердикта `ACCEPT` и зелёного CI; CTO-пути при конфликтах берутся из `master` (решение владельца 04.10).
- Dependabot не используется (решение владельца 04.10). Уязвимости образов выявляет ночной скан `master` (ADR-0012); digest и версии обновляются отдельной задачей.
- Cursor не сбрасывает и не прячет чужие изменения в рабочем дереве.
- Документы CTO — ветки `docs/*`, мержит владелец.
- Сообщения коммитов: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `build:`, `ci:`).
