# ADR-0009 — Квоты пользователей и дневной бюджет LLM

Статус: принято · 2026-10-06 · Автор: Claude (CTO)

## Контекст
Главный операционный риск — стоимость LLM («Исчерпание бюджета LLM» в 03-privacy-and-security). Ключ разработки жёстко ограничен по токенам. Ограничение частоты (30 запросов в минуту на пользователя) не ограничивает расход за сутки. Inline-генерации при наборе текста — самый массовый источник вызовов.

## Решение

### 1. Дневные квоты на пользователя
День — продуктовый: часовой пояс `SP_ANALYTICS_TIMEZONE`, по умолчанию Москва. Квоты считаются по классам операций:
- `inline` — генерации «Смягчить» и «Помоги сказать» в inline. Повторное использование готового результата квоту не расходует.
- `decode` — «Расшифровать» в личке и мини-приложении. `suggest_rule` отдельно не считается: на каждый разбор приходится не больше одного вызова.

Значения задаются настройками. По умолчанию — 300 для `inline` и 40 для `decode` в день (решение CTO D-12; владелец может изменить).

Квота резервируется перед вызовом LLM. Если провайдер недоступен (`unavailable`), резерв возвращается. Отказ модели и невалидный ответ квоту расходуют.

### 2. Глобальный дневной бюджет
Бюджет billable-токенов на продуктовый день — `SP_LLM_DAILY_TOKEN_BUDGET`. Настройка обязательная, значения по умолчанию нет.
- Перед вызовом LLM: если потрачено не меньше бюджета, вызов не выполняется (`budget_exhausted`).
- После вызова фактические billable-токены добавляются к счётчику.
- Возможный перерасход ограничен вызовами, которые уже начались в момент исчерпания.
- Бюджет действует для всех сценариев, включая `suggest_rule`.

### 3. Счётчики
Счётчики хранятся в Valkey: операции атомарные, ключи истекают после конца продуктового дня.
- Если счётчика бюджета нет (например, Valkey перезапустился), он восстанавливается из `usage_events` как сумма billable-токенов за текущий день.
- Квоты пользователей при потере Valkey обнуляются. Это допустимо.

### 4. Кризис вне лимитов
Проверка на кризис выполняется до квот и бюджета и от них не зависит: помощь в кризисной ситуации доступна всегда.

### 5. Что видит пользователь
Понятный текст из общего каталога (бот и API) и время сброса лимита. Текст пользователя в ответ не возвращается.

Пишется событие использования с исходом `limited` и видом лимита (`user_quota` или `global_budget`). Такое событие не считается ни обращением, ни ошибкой (02-architecture §8).

### 6. Сигнал аномалии
Если расход за час превышает `SP_LLM_HOURLY_SPIKE_SHARE` дневного бюджета (по умолчанию 25 %), один раз в час пишется структурированное событие лога `llm_spend_spike`. Алерты по нему — в 0020.

## Альтернативы
- Квоты пользователя в токенах — отклонено: непредсказуемо для пользователя и требует резервировать по `max_tokens`.
- Счётчики в Postgres — отклонено: горячая запись на каждый запрос.
- Только ограничение частоты — не ограничивает расход за сутки.

## Последствия
Расход в день ограничен сверху и известен заранее. Злоупотребление одним аккаунтом ограничено квотой. При исчерпании бюджета сервис честно сообщает о недоступности, но помощь в кризисе продолжает работать.
