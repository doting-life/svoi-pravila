# ADR-0006 — Порт генерации и адаптер GigaChat

Статус: принято · 2026-10-03 · Автор: Claude (CTO) · Редакция 1.1 (п. 4) — 2026-10-03 · Редакция 1.2 (пп. 1, 9, 10) — 2026-10-04

## Контекст
Слой `application` не может импортировать Pydantic и детали провайдера. Сценарии продукта — «Смягчить», «Помоги сказать», «Расшифровать» (последний — со стримингом в личке). GigaChat имеет собственную модерацию и может отказать в ответе на темы конфликтов; доступ требует корневого сертификата НУЦ Минцифры.

## Решение
1. **Порт уровня сценариев, а не «чат-комплишн».** `application/ports/generation.py` объявляет `TextGenerator` с операциями `soften`, `help_say` и `decode_stream` (ред. 1.2: нестриминговая `decode` удалена — у неё нет потребителя; «Расшифровать» живёт в личке и мини-приложении, inline его не поддерживает). Вход и выход — неизменяемые dataclass-ы приложения: текст пользователя, действующие правила контакта (категория, текст, дата вступления), тип отношений, дедлайн; на выходе — варианты с жёсткостью, индексы применённых правил, вердикт безопасности, версия промпта, модель, использование токенов.
2. **Всё, что относится к LLM, живёт в адаптере** `adapters/llm/`: промпты (версионированные файлы-ресурсы пакета), Pydantic-схемы вывода, протокол стриминга, маппинг ошибок провайдера.
3. **Недоверенный ввод.** Текст пользователя и собеседника передаётся между границами со случайным одноразовым маркером на каждый запрос; модель получает явную инструкцию не исполнять инструкции из данных.
4. **Стриминг «Расшифровать» — две фазы** (редакция 1.1, по данным бенчмарка 0005-b). Фаза A — стриминговый вызов без JSON: модель пишет свободный текст разбора; адаптер отдаёт фрагменты (`AnalysisChunk`) как черновой предпросмотр и в конце проверяет полный текст. Фаза B — обычный структурированный вызов `decode` (строгая схема, одна повторная попытка), которому разбор фазы A передаётся как недоверенные данные внутри той же границы. `DecodeCompleted` несёт проверенный разбор и структурированный результат; канал показывает итоговое сообщение только по `DecodeCompleted`, черновик — эфемерный. Один дедлайн на обе фазы.
5. **Ошибки провайдера → ошибки приложения:** недоступность/таймаут/лимит → `GenerationUnavailable`; модерация провайдера (`finish_reason = blacklist`) → `GenerationRefusedByProvider`; невалидный вывод → `InvalidGenerationOutput`. Сообщения исключений провайдера наружу не попадают.
6. **TLS.** Корневой сертификат НУЦ Минцифры хранится в репозитории (публичный, с указанием источника и SHA-256), копируется в образ и передаётся SDK явным путём. Отключение проверки сертификатов невозможно конфигурацией.
7. **Конфигурация только через `Settings`.** Переменные окружения `GIGACHAT_*` SDK не используются; все параметры передаются конструктору явно.
8. **Бенчмарк отдельно от тестов.** Скрипт измеряет p50/p95 латентности, время до первого фрагмента, долю валидного вывода, долю отказов модерации и стоимость по моделям на синтетическом наборе; в тестах провайдер не вызывается.
9. **Модели по сценариям** (бенчмарк 0005-d, 04.10, синтетический набор 22×3): «Смягчить», «Помоги сказать» — GigaChat-3-Lightning (p50 ≈ 0,9 с, валидно 95–98 %); «Расшифровать» — GigaChat-2-Pro (первый фрагмент p50 1,3 с, итог p95 8,2 с, валидно 100 % с первой попытки обеих фаз). Lightning для «Расшифровать» в 15 раз дешевле, но пока не проходит цели качества — пересмотр в 0019 по данным беты в рамках бюджета (перенесено из 0010 решением CTO 04.10: живые прогоны ради пересмотра сейчас не окупают расход ключа).
10. **Бюджет живых вызовов.** Ключ разработки ограничен по токенам. Живые вызовы провайдера — только с явным бюджетом в задаче, после офлайн-проверки метрик, с `--dry-run` и жёстким `--max-tokens` (правило исполнителя `60-live-provider-budget`).

## Последствия
- Смена провайдера — новый адаптер того же порта и прогон бенчмарка/eval.
- Доля отказов модерации GigaChat — продуктовый риск; измеряется бенчмарком и обрабатывается в сценариях бережным сообщением пользователю.

## Изменения
- **1.1 (2026-10-03), п. 4.** Исходный вариант — один стриминговый вызов «разбор → служебный разделитель → JSON» — отклонён по данным 0005-b: ошибка протокола (нет разделителя, битый JSON) обнаруживается только после того, как разбор уже отдан пользователю, поэтому повторная попытка структурно невозможна (доля валидного вывода с первой попытки и после повтора совпадает у всех моделей; GigaChat-3-Lightning — 11 %). Разделение на две фазы переносит JSON в строгий структурированный вызов с повтором, а внутриполосный разделитель (`SPSEP_`) исчезает из протокола.
- **1.2 (2026-10-04), пп. 1, 9, 10.** Нестриминговая `decode` удалена из порта (потребителя нет; структурированный вызов остаётся внутренним шагом фазы B). Зафиксирован выбор моделей по данным 0005-d и правило бюджета живых вызовов. Причина: прогоны 0005-b…d израсходовали порядка миллиона токенов ключа разработки — методика замеров была избыточной (полные наборы × 3 повтора × несколько моделей на каждой итерации).
