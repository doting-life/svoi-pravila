# ADR-0013 — Сообщение без «via @бот»: отправляет сам пользователь

Статус: принято · 2026-10-11 · Автор: Claude (CTO), по итогам тестирования 09.10 и исследования 11.10

## Контекст
На тестах пользователи назвали подпись «via @Svoi_PravilaBot» под отправленным сообщением главным ограничителем: собеседник видит, что текст подготовил бот. Исследование 11.10 показало:
- подпись ставит сервер Telegram на любое сообщение, отправленное через inline-режим (поле `via_bot_id`); в Bot API нет способа её убрать;
- флаг `hide_via` в MTProto работает только для встроенных ботов Telegram и выставляется клиентом пользователя;
- подписи нет только там, где «Отправить» нажимает сам человек: копирование и вставка, ссылка Telegram с готовым текстом в поле ввода, своя клавиатура.

Проверка владельцем 11.10:
- `t.me/share/url?text=…` без параметра `url` не работает — открывает telegram.org;
- `t.me/<username>?text=…` открывает чат с этим пользователем с готовым текстом в поле ввода — на телефоне и на компьютере.

## Решение
1. **Правило продукта.** Наш текст попадает в чужой чат только через действие самого пользователя. Бот никогда не отправляет сообщений от имени пользователя.
2. **Пути:**
   - inline-режим — быстрый путь с подписью «via»; об этом сказано при первом запуске;
   - экран «Смягчить» в мини-приложении: «Скопировать и вернуться в чат» — подходит для любого чата;
   - «Отправить {имя}» для партнёра по общим правилам, если у него есть публичное имя пользователя: ссылка `t.me/<username>?text=…` через `openTelegramLink` открывает чат с готовым текстом. Имя пользователя бот получает в момент запроса (`getChat` по Telegram-идентификатору партнёра) и нигде не хранит;
   - своя клавиатура (Android, затем iOS) — полное решение без лишних шагов; отдельное ADR перед началом работ.
3. **Отклонено:**
   - боты Telegram Business / Chat Automation: пишут только туда, где было входящее сообщение за последние 24 часа; к черновику доступа нет — только правка уже отправленного, с пометкой «изменено»; бот получает весь текст подключённых переписок, что противоречит ADR-0002;
   - `t.me/share/url`: требует адрес сайта, а положить вместо него текст — недокументированное использование;
   - юзерботы, модифицированные клиенты, `hide_via`: нарушают правила Telegram и наши принципы.

## Последствия
- Для партнёра по правилам — два нажатия до отправки без подписи; для остальных чатов — копирование и вставка.
- Имя пользователя партнёра не хранится. Если у партнёра нет публичного имени, остаётся копирование.
- Клавиатура становится главным направлением после беты.

## Дополнение 1 · 2026-10-11 — экран «Смягчить» из inline-режима работает без initData

### Что случилось
В 0026.3 кнопка над inline-результатами («Для: {имя} · без подписи», «Без подписи — в приложении») открывает мини-приложение через `InlineQueryResultsButton(web_app=…)`. На проде 11.10 владелец увидел «Откройте приложение из Telegram» на телефоне и на компьютере.

Причина — ошибка проектирования CTO, а не исполнителя. Документация Telegram о `WebApp.initData`: «It is empty if the Mini App was launched from a keyboard button or from inline mode» (core.telegram.org/bots/webapps). Мини-приложение, открытое из inline-режима, не получает подписанных данных пользователя. Наш клиент считал пустой `initData` признаком «открыто вне Telegram», а сервер принимал только `initData`. Тесты этого не ловили: поддельный адаптер Telegram всегда отдавал `initData`.

### Как Telegram запускает мини-приложение
| Откуда | `initData` | Где у нас |
|---|---|---|
| Кнопка меню, Main Mini App, прямая ссылка `t.me/<бот>?startapp=` | есть, со `start_param` | основной вход, приглашения (`inv_`) |
| Inline-кнопка под сообщением (`InlineKeyboardButton.web_app`) | есть | приветствие, уведомление о правиле (`?view=pending`) |
| Кнопка над inline-результатами (`InlineQueryResultsButton.web_app`) | **пусто** | экран «Смягчить» из inline (0026.3) |
| Кнопка обычной клавиатуры (`KeyboardButton.web_app`) | пусто | не используем |

### Решение
В inline-режиме бот уже знает пользователя: запрос `inline_query` пришёл от Telegram через вебхук с секретом. Telegram прямо предлагает передавать контекст inline-запуска через адрес. Поэтому личность переносит сам одноразовый токен передачи `h`.

1. **Токен передачи — пропуск.** Бот выпускает токен `h` для автора inline-запроса. Ключ расшифровки лежит в самом токене, шифротекст — в Valkey. Внутри зашифрованных данных: внутренний id пользователя, черновик и контакт. Подделать их нельзя: AES-GCM, AAD — назначение и id токена. Токен одноразовый (GETDEL), срок жизни — как у подготовленных результатов.
2. **Обмен на сессию.** `POST /api/v1/compose/handoff/redeem` с заголовком `Authorization: handoff <h>`, без `initData`. Сервер:
   - сжигает токен;
   - проверяет, что пользователь существует и прошёл онбординг с согласием;
   - выдаёт сессию экрана «Смягчить».

   Сессия — такой же запечатанный токен, срок 15 минут, константа в коде. Она привязана к пользователю и к контакту из inline-запроса. Ответ — контекст экрана: черновик, партнёр (id, подпись, публичное имя через `getChat`, если есть), лимиты длины, сессия и время её истечения.
3. **Одна аутентификация, две схемы, явная область.** Зависимость аутентификации возвращает принципала с областью:
   - `tma <initData>` → полная область;
   - `compose <сессия>` → область `compose`.

   В области `compose` доступны только `POST /compose` и `POST /compose/choice`, и только с контактом сессии или без контакта. Остальные маршруты отвечают 403 `scope_insufficient`. Так пропуск не открывает правила, экспорт, удаление аккаунта и прочие разделы. Онбординг и существование пользователя проверяются на каждом запросе, как для `initData`.
4. **Клиент различает три вида запуска:**
   - вне Telegram (`platform` = `unknown`) → «Откройте приложение из Telegram»;
   - с `initData` → полное приложение;
   - внутри Telegram без `initData`, с `?view=compose&h=` → отдельный экран «Смягчить».

   Отдельный экран — без вкладок и без выбора партнёра. Сессия хранится только в памяти страницы. `ready()` и `expand()` вызываются при любом запуске внутри Telegram.
5. **Удаляется:** обмен токена по `initData`; чтение `view=compose` и `h` внутри полного приложения (из inline-режима `initData` не бывает); запасные клиентские лимиты.

### Отклонено
- `InlineQueryResultsButton.start_parameter`: уводит пользователя в личку бота, нужен лишний шаг и служебное сообщение. Личка закрыта по ADR-0010.
- Переоткрыть себя ссылкой `t.me/<бот>?startapp=` из inline-окна: два окна подряд, поведение зависит от клиента. Это обход, а не решение.
- Полная сессия по токену: пропуск из адреса не должен давать больше, чем нужно экрану.

### Инварианты
- В статическом сервере мини-приложения (Caddy) нет журнала доступа с адресами запросов. `Referrer-Policy: no-referrer` сохраняется.
- Токены `h` и сессии не пишутся в журналы. Заголовок `Authorization` любой схемы маскируется.
- Новый маршрут API по умолчанию закрыт для области `compose`. Это закреплено тестом по списку маршрутов OpenAPI.
