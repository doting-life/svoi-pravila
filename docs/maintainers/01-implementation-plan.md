## 0. Рамки проекта (решения владельца от 03.10)
- **Платформа — только Telegram:** бот (inline-режим и личный чат) + мини-приложение. Других мессенджеров нет.
- **Инфраструктура — OVH VPS.** Весь продукт разворачивается на нём, но только после того, как полностью готов и прошёл ручное тестирование.
- **Разработка и ручное тестирование — локально в Docker:** весь стек (приложение, PostgreSQL, Valkey) собирается и запускается теми же образами, что пойдут на VPS (ADR-0005).
- **Наша задача — функционально полный, продакшн-качественный продукт.** Официальный релиз, юридическое оформление (тексты согласий, политика, уведомления регуляторов, выбор юрисдикции хранения), дистрибуция и отчётность перед программой — зона выпускающей стороны.
- Отсюда инженерное требование: продукт **переносим** (разворачивается на любом Linux-сервере одной процедурой) и **технически готов** к юридическому оформлению: версионируемые согласия, экспорт и удаление данных, шифрование, отсутствие хранения переписки.

## 1. Что строим

AI-помощник для трудных разговоров, работающий там, где человек печатает.

| Сценарий | Вход | Выход |
|---|---|---|
| **Смягчить** | черновик пользователя, написанный на эмоциях | тот же смысл и та же претензия без атаки; не «вежливая пустышка» |
| **Расшифровать** | входящее сообщение от собеседника | разбор подтекста, «чего человек на самом деле просит», 3 варианта ответа разной жёсткости |
| **Помоги сказать** | намерение («отказать», «поставить границу», «признать вину», «вернуться к разговору после ссоры») | готовое сообщение |

**Ядро продукта — «Свои Правила»**: для каждого важного контакта ведётся свод договорённостей (о каких темах не говорим, как принято просить, что считается извинением). Свод подставляется в контекст модели, пополняется по сигналам (какие варианты отправлены, какие отклонены) и может быть **двусторонним**: оба участника видят один свод, приглашение второго встроено в основной сценарий.

**Целевые характеристики продукта:** ответ < 1,5 с; обработка только по явному действию пользователя; продукт выдерживает 1000+ DAU × 25–35 обращений на DAU.

**Нефункциональные требования CTO:** тексты переписки не сохраняются; свод правил шифруется на уровне приложения; доменная логика покрыта тестами на 100 %; воспроизводимые сборки; регрессии качества ответов ловятся eval-набором; переносимое развёртывание.

## 2. Инженерные ограничения, которые формируют решение

### R1. Ограничения Telegram
| Ограничение | Следствие для дизайна |
|---|---|
| Текст inline-запроса ≤ 256 символов | inline — для коротких черновиков; длинные тексты и «Расшифровать» — через личку с ботом или мини-приложение |
| Inline-запрос не сообщает, в каком чате и с кем пишет пользователь | контакт (свод правил) выбирается явно: активный контакт по умолчанию + префикс-тег + кнопка смены в мини-приложении; привязка к чату — через `chat_instance` из callback под inline-сообщением |
| Пересылать входящее в inline нельзя | «Расшифровать» = переслать сообщение боту → разбор → «Вставить в чат» / «Копировать» |
| Guest Mode и ephemeral-сообщения (Bot API 10.x) оставляют видимый другим след вызова и не работают приватно в личных чатах | «Расшифровать» в группах и чужих чатах не делаем в MVP — ADR-0007 (спайк 0012) |
| Сообщение, отправленное через inline, получатель видит с пометкой «via @bot» | D-5: вставка через inline + всегда доступное «Копировать» |
| Стриминга в ответ на inline-запрос нет | inline-ответ короткий и быстрый; стриминг (`sendMessageDraft`, Bot API 9.5+) — в личке |
| Telegram шлёт inline-запрос по мере набора | серверная отмена устаревших запросов, минимальная длина, кэш; иначе стоимость инференса растёт кратно |
| `chosen_inline_result` приходит только при включённом inline feedback | включить на 100 % в BotFather — главный сигнал обучения правил |
| Кнопка копирования ограничена по длине (уточнить по спецификации) | длинные варианты копируются через мини-приложение |
| Bot API 10.x: guest mode и ephemeral-сообщения (только группы) | R&D-спайк в Спринте 2 |

### R2. Приватность как инженерное требование
Тексты об отношениях — данные особой чувствительности (частная и интимная жизнь пользователя и третьих лиц). Независимо от юрисдикции релиза продукт обеспечивает:
- обработку только явно переданного текста; переписка не хранится;
- отбрасывание метаданных третьих лиц (отправитель пересланного сообщения) на границе адаптера;
- шифрование свода правил на уровне приложения, crypto-shredding при удалении;
- механизм раздельных версионируемых согласий (тексты — черновики, финальные утверждает выпускающая сторона);
- экспорт и удаление данных пользователем;
- отсутствие внешних SaaS для логов, ошибок и аналитики.

### R3. LLM
- Выбран **GigaChat** (D-2; доступ к API владелец создал 03.10; async SDK со стримингом, structured output, function calling). Модели Lite / Pro / Max; цены на 29.09.2026 — 0,065 / 0,5 / 0,65 ₽ за 1k токенов.
- Сетевая доступность проверяется бенчмарком из локального Docker (0005) и повторно с OVH VPS при развёртывании (0023). Для TLS нужен корневой сертификат НУЦ Минцифры в trust store образа; отключать проверку TLS запрещено.
- Цель < 1,5 с подтверждается бенчмарком латентности и качества по моделям (Спринт 1).
- Провайдер скрыт за портом `LLM`: замена — новый адаптер + прогон eval, домен не меняется.

### R4. Безопасность пользователей
- Отказ помогать с манипуляцией, угрозами, давлением, слежкой, преследованием.
- Кризисные сигналы (угроза насилия, самоповреждение) → бережный ответ и контакты помощи из каталога по локали вместо генерации.
- «Расшифровать» формулирует гипотезы, а не утверждения о чужих намерениях.
- Возраст 18+ (D-8). Входящий текст собеседника — недоверенный ввод (prompt injection).

### R5. Сроки
Сегодня 03.10. Ручное тестирование рабочего MVP в локальном Docker — **15.10**. Функционально полный продукт — **04.12**; выход на VPS — после полной ручной приёмки.

## 4. Архитектура (выжимка; полная версия — `02-architecture.md`)

### 4.1 Принципы
1. **Hexagonal / ports & adapters.** Домен и сценарии — чистый Python без I/O; Telegram, LLM, БД, кэш — адаптеры за портами. Даёт тестируемость на 100 % и замену LLM без переписывания. Границы проверяются import-linter.
2. **Privacy by design** (R2).
3. **Единый источник контрактов:** Pydantic → OpenAPI → сгенерированный TypeScript-клиент мини-приложения.
4. **Детерминированность качества:** промпты LLM версионируются, каждая версия проходит eval.
5. **Ничего временного.**

### 4.2 Стек (точные версии фиксирует bootstrap-задача по lock-файлам)
| Слой | Выбор | Почему |
|---|---|---|
| Язык бэкенда | Python 3.13 | SDK GigaChat поддерживает 3.8–3.13 |
| Пакеты | uv (lock-файл) | воспроизводимость, скорость |
| HTTP | FastAPI + Uvicorn | webhook + API мини-приложения в одном ASGI-приложении |
| Telegram | aiogram 3.31+ (Bot API 10.3) | async; `sendMessageDraft`, inline, мини-приложения |
| Валидация/конфиг | Pydantic v2, pydantic-settings | |
| БД | PostgreSQL 18, SQLAlchemy 2 (async) + asyncpg, Alembic | |
| Кэш/лимиты | Valkey | rate limit, дедупликация `update_id`, prepared results |
| LLM | `gigachat` SDK (async) за портом `LLM` | |
| Криптография | `cryptography` (AES-256-GCM, envelope encryption) | |
| Логи/метрики | structlog (JSON, редактирование ПДн), Prometheus | |
| Качество | ruff, mypy --strict, import-linter, pytest, hypothesis, pip-audit, gitleaks, trivy | |
| Мини-приложение | Vite + React + TypeScript strict, Telegram Mini Apps SDK, TanStack Query, клиент из OpenAPI, Biome, Vitest | статическое SPA: SSR не нужен внутри WebView |
| Доставка | Docker (multi-stage, non-root), docker compose, Caddy (автоматический TLS), GitHub Actions | один VPS, переносимо |

### 4.3 Ключевые потоки
- **Inline «Смягчить» / «Помоги сказать»:** update → secret token → дедупликация → rate limit → отмена предыдущего запроса пользователя → сценарий (правила активного контакта + текст) → LLM structured output (2–3 варианта, применённые правила, флаг безопасности) → `answerInlineQuery` (`is_personal`) → `chosen_inline_result` → событие «обращение» + сигнал для правил.
- **«Расшифровать» в личке:** пересланное/вставленное сообщение → метаданные отправителя отбрасываются → стриминг разбора (`sendMessageDraft`) → итоговое сообщение с тремя вариантами и кнопками «Копировать» / «Вставить в чат» (`switch_inline_query_chosen_chat` + одноразовый токен prepared result в Valkey).
- **Мини-приложение:** аутентификация по `initData` (HMAC, свежесть) → контакты, свод правил, предложения правил, приглашение второго (одноразовая deep link, 128 бит, хранится хэш, TTL 7 дней), настройки приватности. Также — работа с длинными текстами по всем трём сценариям.
- **Предложения правил:** выбор/отклонение вариантов → LLM формулирует кандидата → пользователь подтверждает.

### 4.4 Данные
`users` · `consents` · `contacts` · `pairs` / `pair_members` · `rules` + `rule_revisions` (зашифрованы, даты для цитаты «вы договорились 12 сентября») · `rule_suggestions` · `invites` (хэш токена) · `usage_events` (без текста, псевдоним пользователя) · `user_keys` (DEK, обёрнутый KEK).

### 4.5 Метрики продукта
DAU, обращения на DAU (D-9), D1/D7, латентность по сценариям — из `usage_events`; ежедневные агрегаты; дашборд Grafana (только агрегаты), доступ — только через SSH-туннель.

## 6. Definition of Done — для каждой задачи
1. Сделано ровно то, что в промпте; вне скоупа — ничего.
2. Гейты зелёные: `ruff check`, `ruff format --check`, `mypy --strict`, `lint-imports`, `pytest` с порогом покрытия, `pip-audit`, `gitleaks` (+ фронтенд-гейты после 0013).
3. Покрытие: `domain`/`application` — 100 % строк и веток; адаптеры — ≥ 90 %; общее — ≥ 95 %.
4. Нет `TODO`, закомментированного кода, заглушек, подавлений без явного разрешения в промпте.
5. Мёртвый код и неиспользуемые зависимости удалены.
6. Миграции обратимы и проверены в CI.
7. Тексты переписки не логируются и не сохраняются — есть тест.
8. Отчёт Cursor в чате по шаблону.
9. Моя проверка исходного кода — ACCEPT.

## 7. Риски
| Риск | Вероятность | Влияние | Митигирование |
|---|---|---|---|
| GigaChat API недоступен из локальной сети или с OVH, либо медленный из-за сетевого пути | средняя | высокое | проверка бенчмарком в 0005 (локально) и при развёртывании в 0023; порт `LLM` позволяет сменить провайдера |
| Латентность > 1,5 с | средняя | высокое | бенчмарк в 0005; лёгкая модель для inline; короткий вывод; отмена устаревших запросов |
| Стоимость inline-запросов при наборе | высокая | среднее | отмена, минимальная длина, кэш, квоты |
| Сдвиг сроков | высокая | высокое | жёсткий скоуп спринтов; лишнее переносится, а не делается наспех |
| Злоупотребления (манипуляция, давление) | средняя | высокое | 0008; eval-кейсы на отказ |
| Утечка свода правил | низкая | критическое | шифрование на уровне приложения, минимум данных, укрепление сервера, ревью угроз |
| Единственный VPS — точка отказа | средняя | среднее | шифрованные бэкапы вне VPS, проверенное восстановление, runbook переразвёртывания |
