# ADR-0005 — Локальный полный стек в Docker до выхода на VPS

Статус: принято · 2026-10-03 · Решение владельца, оформил Claude (CTO)

## Контекст
Владелец собирает и разворачивает весь продукт локально в Docker для ручного тестирования и переносит его на OVH VPS только после полной готовности и успешной ручной приёмки. Telegram доставляет обновления боту либо через webhook (нужен публичный HTTPS-адрес), либо через long polling (исходящие запросы бота, публичный адрес не нужен).

## Решение
1. **Один набор образов.** Локальный стек и VPS используют одни и те же образы приложения; отличия — только в конфигурации окружения и в составе сервисов compose (на VPS добавляются Caddy и бэкапы).
2. **Полный стек в compose:** приложение, одноразовый шаг миграций (запускается до приложения, приложение стартует только после его успешного завершения), PostgreSQL, Valkey. Управление — цели `make` (`up`, `down`, `logs`, `ps`).
3. **Получение обновлений Telegram — режим из конфигурации:** `polling` локально, `webhook` на VPS. Оба режима передают обновления в один и тот же обработчик; бизнес-логика не знает о режиме. В режиме `polling` webhook бота снимается при старте, в режиме `webhook` — устанавливается с secret token.
4. **Мини-приложение** при локальной разработке открывается через HTTPS-туннель или тестовое окружение Telegram; способ выбирается в задаче bootstrap мини-приложения (0013).
5. **Секреты локально** — только в `.env` с правами 600; на VPS — в файле окружения сервера вне репозитория.
6. **Выход на VPS** — отдельная задача (0023) после полной ручной приёмки.

## Последствия
- Ручное тестирование 15.10 проходит на локальном стеке с тестовым ботом.
- Проверка сетевой доступности GigaChat выполняется дважды: из локального Docker (0005) и с VPS (0023).
- Конфигурация развёртывания отделена от кода приложения; переход на VPS не меняет образы.
