# Процесс работы: CTO ↔ исполнители ↔ владельцы

Владелец документа: Claude (CTO). Исполнители этот документ не редактируют.
Редакция: 2.1 · 2026-10-13 (ред. 2.1 — бэклог, дорожная карта и этапы; ред. 2.0 — ADR-0014: задачи в GitHub Issues, отчёты в PR, единые правила `AGENTS.md` для всех инструментов; ред. 1.4 — экономия токенов исполнителя)

Правила для исполнителей — в `AGENTS.md` (корень и области). Этот документ описывает процесс для людей.

---

## 1. Роли

| Роль | Кто | Делает | Не делает |
|---|---|---|---|
| CTO | Claude | архитектура, ADR, задачи (Issue), проверка результата **по исходному коду**, ревью PR, решения о зависимостях | не пишет код; не сливает PR; не трогает сервер |
| Владелец (релизы и сервер) | человек | решения, одобрение и слияние PR второго владельца, релизы, сервер, ключи прода, приёмка в Telegram | — |
| Владелец | человек | решения, одобрение и слияние PR второго владельца, приёмка | доступа к серверу нет |
| Исполнитель | Cursor, GitHub Copilot (локально, режим агента) — в руках владельца | реализует одну задачу, гоняет проверки, отчитывается в PR | не сливает, не пушит в `master`, не трогает CTO-пути, сервер и ключи прода |

## 2. Жизненный цикл задачи
1. **Issue.** CTO создаёт задачу по шаблону «Task (CTO)»: ветка, исполнитель, цель, что читать, требования, вне скоупа, приёмка, бюджет живых вызовов. Промпт пишется на английском.
2. **Ветка** `task/NNNN-slug` от свежего `master`.
3. **Работа.** `make quick` во время работы; полный `make ci` — один раз, автоматически, перед push.
4. **PR.** Заголовок `NNNN — …`, описание — отчёт по шаблону, `Closes #<issue>`. GitHub CI идёт параллельно, его не ждут.
5. **Проверка CTO.** Diff и исходный код, проверки CTO сам; отчёт — только навигация.
6. **Вердикт** — ревью PR. `CHANGES REQUIRED` содержит промпт `NNNN-a` со списком дефектов; исправление — в том же PR, новый отчёт — комментарием.
7. **Слияние.** Squash-merge после ACCEPT и зелёного CI. Сливает владелец; свой PR одобряет второй владелец.
8. **Релиз** — владелец (релизы и сервер). **Приёмка** в Telegram — владельцы. Issue закрывается слиянием.
9. **Блокер.** Исполнитель останавливается, пишет отчёт `Status: BLOCKED` с вопросом и ставит `needs:cto`.
10. **Живые вызовы LLM — только с бюджетом** в Issue; ключ у каждого исполнителя свой, с дневным лимитом.
11. **Технический долг не копится.** Дефект, найденный при проверке, исправляется до слияния.

## 3. Метки

| Метка | Смысл |
|---|---|
| `task` | задача CTO |
| `proposal` | предложение команды |
| `needs:cto` | ждёт ответа CTO |
| `needs:owner` | ждёт решения владельцев (продукт, бюджет, сервер, ключи) |
| `area:backend`, `area:miniapp`, `area:infra` | область |
| `executor:cursor`, `executor:copilot` | исполнитель |
| `backlog` | пункт плана; исполнители его не берут, пока CTO не выпустит по нему задачу `task` |
| `roadmap` | Issue «Дорожная карта» — общий список работ по этапам |

Этапы — milestones GitHub (M1…M4). Каждый пункт `backlog` и каждая задача относятся к этапу; порядок работ — в Issue «Дорожная карта». Пункты добавляет и переупорядочивает CTO; когда пункт становится задачей, CTO переписывает его по форме «Task (CTO)» и меняет метку `backlog` на `task`.

## 4. Как команда общается с CTO
- Вопрос по задаче — комментарий в Issue или PR + `needs:cto`.
- Идея или улучшение — Issue «Proposal» (метки ставятся сами).
- Замечание к строке — комментарий к строке в PR.
- CTO отвечает там же. Решения, которые принадлежат владельцам, CTO оформляет вариантами с рекомендацией и ставит `needs:owner`.
- CTO работает, когда владелец открывает сессию («проверь GitHub») или по расписанию, если владельцы его включат.

## 5. Гейты
Единая точка — `make`: `make quick` в работе, `make ci` в хуке перед push (по области изменений), полный набор — на GitHub при push в `master` и по расписанию. Скан образов — по ADR-0012. Состав проверок: ruff, mypy `--strict`, import-linter, pytest с порогами покрытия, pip-audit, gitleaks, синхронность и обратимость миграций, проверки мини-приложения (`pnpm check`), сборка образов, smoke стека, проверка владения CTO-путями.

## 6. Защита `master` (настраивают владельцы)
Только через PR; обязательные проверки CI; только squash; запрет force-push и удаления; обязательное одобрение CODEOWNERS (команда `builders`). Документы CTO тоже идут через PR.

## 7. Конфиденциальность
Репозиторий публичный. Никаких имён, логинов, e-mail, локальных путей, названий компаний, доменов и IP прода, секретов, пользовательских данных и деловых материалов — ни в коде, ни в коммитах, ни в Issue и PR. Только роли.

## 8. Экономия токенов
- Issue самодостаточна; исполнитель читает только указанные разделы и правила своей области.
- Отчёт — короткий шаблон; без скриншотов, таблиц покрытия и пересказа кода.
- Один push на раунд ревью; исправления — в том же PR.
- Режим агента — обычный; усиленные режимы моделей — только если Issue это требует.
- Сессии CTO — по блоку работы; контекст живёт в репозитории (`00-status.md`, ADR), а не в длинном чате.
